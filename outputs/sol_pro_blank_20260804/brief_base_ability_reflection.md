## 1. プロジェクトの前提（必要な分だけ）

個人用の野球ペナントシミュレーターを作っています。実在NPB選手の実成績から、ゲーム内の能力値（ミート・パワー等、1〜130の連続値）を逆算する「査定」を作っています。

設計の縛り（このプロジェクト全体で守っている原則）:

- **係数のハードコード禁止**: 「打率の差1厘につき能力0.3ポイント」のような、根拠のない変換係数を新設してはいけない。数値変換が必要なら、**既に較正済みの変換関数を再利用する**か、**実測から導出可能な形**にする。
- **二重計上禁止**: 同じ情報（同じ観測事実）を、2つの調整に別々に使って両方で効かせてはいけない。
- **最終的な答え合わせは「12球団×143試合をシミュレートした時、リーグ全体の成績分布が実データの分布と一致するか」**（打率.250前後、本塁打王40本台等）。ただしこのエンジン側の検証はまだ実施できていない。

## 2. 4層分離（正本の仕様、逐語）

```text
補正成績
= 年度・リーグ・球場・サンプルを補正した統計

平均得能込み基準
= 同じ補正成績帯の平均的な得能を含む能力

個別査定能力
= 当該選手に付ける得能との差を反映した基礎能力

実効能力
= ゲーム内で基礎能力と得能を合成した性能
```

能力表には、どの層の数値かを必ず明記する。

**今回設計してほしいのは第3層「個別査定能力」の作り方**です。

## 3. ミートの基準統計（正本の仕様、逐語）

### 3.1 基準統計

理想:
```text
AVG_neutral_raw = AVG_vsR_nonRISP
```
（対右投手・非得点圏、という「打者の素の対応力に一番近い」文脈の打率）

データ階層:

| 階層 | 入力 | 処理 |
|---|---|---|
| A | 対右×非得点圏のH/AB（交差セルの実測） | 直接使用 |
| B | 対右、対左、RISP、non-RISPの周辺値（交差セルなし） | 対右を暫定基準。交差値を捏造しない |
| C | 総合のみ | 総打率を暫定使用し、信頼度を下げる |

REJECTED（禁止されている式）:
```text
AVG_vsR - 0.30 × (AVG_RISP - AVG_nonRISP)
```
理由: 周辺集計（対右の合計・得点圏の合計）だけでは、交差セル（対右かつ得点圏）を一意に求められない。任意の係数（0.30）で交差を作ってはいけない。

### 3.2 実データの現実

- 交差セル（対右×非得点圏）は、このプロジェクトが使える公開データのどこにも存在しない。**階層Aには原理的に到達できない。**
- 実際に得られるのは: 総合のH/AB、対右投手のH/AB、対左投手のH/AB、得点圏のH/AB、非得点圏のH/AB（この5つは別々の集計で、交差は取れない）
- 典型的なサンプルサイズ（レギュラー選手、1シーズン）: 総合打数400〜600、対左投手打数100〜200、対右投手打数300〜450、得点圏打数100〜160、非得点圏打数300〜450

### 3.3 得能調整（正本の仕様、逐語）

方向:
```text
青得能が同成績帯平均より多い → 基礎Mを下げる
赤得能が多い → 基礎Mを上げる
```
（「チャンス」＝得点圏の得意・不得意、「対左」＝左投手への得意・不得意、が青得能・赤得能の代表例）

具体点数はOPEN。ゲーム内シミュレーションで校正する、とされている。

### 3.4 二重計上禁止（正本の仕様、逐語）

> 完全な`AVG_vsR_nonRISP`を使った後に、チャンスB・対左Bを理由にさらにMを下げない。
> 調整台帳に、各要素がどこへ入ったかを記録する。

## 4. パワー（本塁打）側の対応する仕様

パワーの基準統計も、ミートと同様に環境補正・小サンプル縮小を経て「500打席相当の本塁打数」というアンカー軸へ変換される。得能の反映方向（青得能が多ければ下げる／赤得能が多ければ上げる）はミートと同じ原則が及ぶと考えられるが、**パワー側について§5.1に相当する基準統計の階層（Tier A/B/C）は仕様上明記されていない**。

対左投手への本塁打の出やすさ・出にくさ（対左のパワー版）を測る場合、実データの制約:
- 本塁打は稀な事象（1シーズン20〜40本程度、対左投手だけに絞ると数本〜十数本）
- 対左投手の打数は100〜200程度（上記3.2と同じ）

## 5. 中心の問い

**「AVG_vsR_nonRISPを基準にする（§5.1の階層B/C）」ことと、「チャンス・対左の得能差分を基礎能力から引く（§5.4/§5.5）」ことは、同じ補正を2つの経路で行おうとしているように見える。**

- 階層B（対右を基準に採用する）は、暗黙のうちに「対左の効果を基準から除く」ことをしている
- 得能調整（対左の得能差分を引く）も、「対左の効果を基礎能力から除く」ことをしている
- 両方を同時に適用すると、対左の効果を二重に除いてしまう可能性がある。逆に、階層Bを字義通り「対右のH/ABをそのまま基準にする」で実装すると、対左の得能調整をする余地がなくなる（既に基準側で対右に寄せているため）

**設計してほしいこと**:

1. **§5.1の文脈階層（A/B/C）と、§5.4/§5.5の得能反映（チャンス・対左の差分を基礎能力から引く）は、同じ1つの機構として設計すべきか、別の機構として設計すべきか。** 別にするなら、二重計上を構造的に防ぐ具体的な方法を示してほしい（「気をつける」ではなく、設計上そもそも両方が効かない形にする）
2. **チャンス（得点圏）と対左（投手左右）は、同じ打席を別々の軸で切っている**（左投手×得点圏の打席は両方の集計に入る）。この重なりをどう扱うべきか。無視してよい条件、無視すべきでない条件を示してほしい
3. **本塁打（パワー）のような稀な事象について、対左右の差を基礎能力へ反映する設計は、ミート（打率）と同じ方法で良いか、それとも別の設計が要るか。** 本塁打の対左サンプルが一桁〜十数本しかないという制約を踏まえて答えてほしい
4. **上記の設計を採用してよいかどうかの受け入れ基準（何を確認できたら採用してよいか）を、投入前に決めてほしい。** 「パワプロ等の外部の値との一致」は、このプロジェクトでは参考程度の位置づけであり、採否を決める基準にはならない。使ってよい基準は (a) 仕様の設計原則との整合 (b) 観測されたデータが実際に測定可能な量なのか、それとも測定誤差（サンプルサイズに起因する偶然のばらつき）に埋もれているか (c) 最終的にはエンジンでのリーグ分布一致（ただし本タスクの時点では未実施）

**係数を1つも新設せずに設計してください。** 数値変換が必要な箇所があれば、「どの既存の較正済み関数を再利用するか」「実測からどう導出するか」を明示し、任意の点数（「+5点」「0.3倍」等）を置かないでください。
