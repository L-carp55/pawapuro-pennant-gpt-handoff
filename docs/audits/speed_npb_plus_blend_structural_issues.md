# 現行 `NPB+ → PowerProラベル回帰 → blend` の構造上の問題

作成日: 2026-08-13
状態: **整理（指示②）**。実装変更はしていない。
関連: `speed_scale_diagnosis_2026.md` / `speed_rolling_holdout_2026.md` / `speed_npb_plus_2026_and_cv.md`

---

## 0. 現行の経路

```text
NPB+アプリの最高速度(km/h)
  ↓ ① 変換式  走力点 = -175.93 + 7.642 × 速度
  │    （scripts/calibrate_npb_plus_direct.mjs が
  │      SELECT power ... FROM pawapuro_full = PowerProの能力値へ回帰して作った）
  ↓ ② 混合    最終値 = 統計値 × (1-w) + 変換値 × w      w = 0.762
  │    （src/cards/pipeline.mjs の blendDirect。w は上の変換式の test_r をそのまま使用）
  ↓ ③ 目盛り  applyScale を**通らない**
最終の走力
```

問題は5つあり、**互いに独立ではなく積み重なっている**。

---

## 1. 目標変数が現実ではなくPowerProの査定値

変換式①の目標変数は**PowerProの能力値**であって、実際のプレー結果ではない。

含意:

- **PowerProの誤り・据え置き・独自の設計思想を、そのまま自作査定へ取り込む。**
  実測で PowerPro据え置きの疑い（SUPPORTED 16人 / POSSIBLE 36人）が確認されているので、
  これは仮定ではなく実在する汚染経路
- 2026-07-31オーナー確定「KONAMI比較は参考チェックに格下げ」と衝突する。
  参考チェックのはずのものが、**変換式の教師値**として査定の内部に入っている
- 同じ誤りをパワーで2026-08-06に修理済み（パワプロラベル由来の実測変換が
  オーナー裁定のアンカーを上書きし、山川穂高の裁定値89.8が78.9まで落ちていた）。
  **走力では同じ構造が残っている**

## 2. 混合の重みも、現実ではなくPowerPro一致度から来ている

重み `w = 0.762` は変換式①の **test_r**（PowerProとの一致度）をそのまま使っている。

つまり「**PowerProとよく一致する変換ほど強く効かせる**」という設計になっている。
現実のプレー結果をどれだけ当てるかは、重みの決定に一切入っていない。

さらにこの test_r は **n=14** で、同じモデルの **test_mae は 10.55点**。
相関だけを見て採用し、誤差を見ていない（この型の誤りは
`feedback_priority_rule_needs_precision_check` に記録済み）。

## 3. 回帰の予測値は必ず幅が縮む（平均への回帰）

変換式①は回帰式なので、その予測値は目的変数より**必ず幅が狭くなる**。
幅の狭い量を重み0.762で混ぜれば、結果も縮む。

実測（`speed_scale_diagnosis_2026.md`）:

```text
統計のみ（較正あり）  幅 14.0
現行の混合後          幅  9.1
PowerPro 2026        幅 15.4
```

**これは測定誤差ではなく数学的な帰結**なので、データを増やしても直らない。
混ぜ方を変えるか、混ぜないかのどちらかでしか解消しない。

## 4. 目盛りの違う2つの量を混ぜている（③の配線）

`blendDirect` は `applyScale` を通らない。理由は記録されており妥当な意図がある——
変換値①は既にPowerProの目盛りに乗っているので、PowerPro由来の較正を再度当てると二重になる。

**だが混ぜる相手（統計値）は較正前の目盛りに乗っている。**

```text
変換値①      … PowerProの目盛り
統計値        … 較正前の生の目盛り
混合結果      … どちらの目盛りでもない
```

実測: 較正が掛かった選手は **98人中1人**。
つまり「走力が低く出る」を直すために2026-08-01に入れた較正は、
**2026年の100人にはほぼ誰にも届いていない**。

## 5. PowerProが prior と QA の両方になる（循環）

変換式①がPowerProラベル由来である以上、混合後の値は**PowerProへ引き寄せられる**。
その値をPowerProと突き合わせて「一致している／乖離している」を判定すると、
**priorとQAが同一情報源**になり、一致率は設計上ほぼ自動的に上がる。

100人レビュー表の `raw_diff` を読む時、この循環を勘定に入れる必要がある。

---

## 6. 「NPB+が悪い」ではない — 悪いのは経路

**測定そのものには実の信号がある。** 選手単位5-fold cross-validation で、
NPB+単独から各アウトカムを直接推定しても fold外で成立している:

```text
fold外 r   triple +0.329 / gdpAvoid +0.438 / infieldHit +0.487 / advance +0.308 / ubr +0.477
平均だけを出すbaselineに対する改善  3.7〜14.2%
```

したがって **NPB+データを捨てる理由はない**。問題は上の1〜5であって測定ではない。

## 7. ただし「経路を直せば上乗せが得られる」も、現時点では確認できていない

2026年の実戦結果（advance）に対して、統計モデル（2026の情報を一切含まない）に
NPB+（2026計測）が上乗せするかを測ると:

```text
下限 5   n=75  統計+0.531  NPB++0.304  増分 -0.032
下限10   n=52  統計+0.621  NPB++0.408  増分 +0.000
下限15   n=28  統計+0.662  NPB++0.341  増分 -0.072
下限20   n=15  統計+0.754  NPB++0.304  増分 -0.194
```

**どの閾値でも増分はゼロ以下。** しかもNPB+は当てる年と同年の計測＝NPB+に有利な条件。
有利な条件で増分が出ないので、これは**負けた側の強い結論**として読める。

現在の理解は「NPB+が悪い」でも「経路だけが悪い」でもなく、
**統計モデルが既に同じものを捉えており冗長**。

---

## 8. 整理: どれを直すと何が解決するか

| 問題 | 直し方 | 解決するもの | 残るもの |
|---|---|---|---|
| 1. 目標変数がPowerPro | 変換式を実プレー結果へ当てはめ直す | PowerPro汚染の遮断 | 幅の縮み（3）は残る |
| 2. 重みがPowerPro一致度 | 重みを実プレー結果での寄与から決める | 同上 | 7の「上乗せが無い」は残る |
| 3. 回帰予測は縮む | 混ぜない／縮みを戻してから混ぜる | 幅の問題 | — |
| 4. 目盛りが二重 | 混ぜる前に両方を同じ目盛りへ揃える | 幅の問題・系統ずれ+14.4点 | — |
| 5. 循環 | PowerProをpriorから外しQA専用へ戻す | 一致率が指標として機能する | 目盛りの正本が空く（下記） |

**5を直すと `scale_calibration.走力 slope=1.3811` もPowerPro由来なので同時に問題になる。**
これは順位・相対モデルとは別の「0〜100の絶対目盛り」の問題として保持する（本書の範囲外）。

## 9. 本書が判定していないこと

- (c)（blendを外す）の採否。rolling holdout では `NOT_IDENTIFIABLE`、
  2026テストでは増分ゼロ以下だが、**どちらもNPB+側に有利な非対称が残る条件**での結果
- 0〜100の絶対目盛りの正しさ
- 統計材料が薄い選手に限れば上乗せがあるか（層別未実施 = T-0203）
