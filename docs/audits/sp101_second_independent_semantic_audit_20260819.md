## Finding 1 — MB-01 method labels do not implement three distinct methods

Severity: **P0**

File: `scripts/sp101_repair_and_regenerate_20260818.py`, `build_mb01()`.

The implementation computes one nearest MLB candidate per current target using the same league-season-percentile feature vector and the same `l2()` distance. The three emitted methods then reuse that same candidate and same distance:

- `MUTUAL_KNN`
- `CALIPERED_MAHALANOBIS`
- `OPTIMAL_TRANSPORT`

Only the caliper and mutual-neighbor condition differ. No covariance matrix / inverse covariance is computed for Mahalanobis distance, and no transport plan / distribution-coupling optimization is computed for optimal transport.

Therefore the reported `211` valid analog rows are **not evidence that all three required algorithms were executed**.

### Required repair

- Keep the current normalized L2 nearest-neighbor route as a baseline, with an honest method name.
- Implement actual mutual kNN.
- Implement actual calipered Mahalanobis (or explicitly documented diagonal standardized distance if covariance is unidentifiable; do not call ordinary L2 Mahalanobis).
- Implement actual optimal-transport/distribution matching, or close that method with a measured computational/data negative finding.
- Emit method-specific candidate sets, distances, balance diagnostics and common-support results.
- Add QA proving the three method outputs are not generated by one shared L2 candidate lookup unless the equality is a measured coincidence.

## Finding 2 — MB-02 holdouts are receipts, not executed validation

Severity: **P0**

File: `scripts/sp101_repair_and_regenerate_20260818.py`, `build_mb02()`.

The shared-indicator ridge model is fit on all usable rows by `fit_shared_model()` and reports in-sample residual metrics.

`player_clustered_holdout` currently stores only metadata:

- status `GROUPED_HOLDOUT_RECEIPT`;
- number of groups;
- a text rule saying MLBAM IDs must not split across train/test.

No held-out predictions, MAE/RMSE/correlation, fold counts or train/test receipts are computed.

Likewise `forward_season_holdout` stores only a list of seasons and a leakage-guard sentence; no forward train/test fits or held-out errors are executed.

The Show edition effect is also described in prose rather than estimated/tested or closed with a measured negative finding.

### Additional target-definition problem

`show_by_id_season[(mlbam_id, season)] = speed` overwrites repeated Live observations in the same player-season. The selected target can therefore depend on row order rather than an explicit snapshot/median/latest-defined policy. If no same-season row exists, the model falls back to a player-wide median across seasons without an explicit temporal-gap feature.

### Required repair

- Define the The Show player-season target deterministically (e.g. season median, explicitly selected baseline snapshot, or update-time panel model) and persist that policy.
- Execute genuine MLBAM-clustered cross-validation with held-out predictions and metrics.
- Execute forward-season validation where identifiable; otherwise store measured insufficiency with denominators.
- Test/estimate edition/update effects where data support them; otherwise close with measured evidence.
- Preserve temporal gaps when cross-time fallback is used; do not silently use a lifetime/player-wide median as same-season truth.
- Retain the existing legacy Sprint Speed submodel separately.

## Finding 3 — MB-07 creates unsupported faster/slower edges

Severity: **P0 / invalid evidence fabrication risk**

File: `scripts/sp101_repair_and_regenerate_20260818.py`, `rebuild_graph()`.

Three invalid constructions are present.

### 3a. Similarity analog is converted into an ordinal direction

For every valid MB-01 analog, the code emits:

- current target = `faster_player`;
- matched MLB analog = `slower_player`.

But an analog match means **similarity**, not that the current NPB player is faster. Feature distance has no sign and cannot establish a faster/slower relation.

### 3b. Community/scouting claims are compared with an arbitrary other player

When a player has a community/powerpro-rating context row, the code chooses:

`next(candidate for candidate in current_packets if candidate != target)`

and uses that unrelated player as the opposite side of an ordinal edge. No source claim compares those two players.

This invents a pairwise relation not supported by the source.

### 3c. Transition direction is converted into an arbitrary speed relation

For NPB→MLB or MLB→NPB transitions, the code again selects an arbitrary other current player and emits the transition player as faster and that arbitrary player as slower.

A league transition contains no pairwise speed direction whatsoever.

### Required repair

- Remove all unsupported MB-01 similarity→faster/slower edges.
- Represent analogs as similarity constraints/neighborhood links, not ordinal edges, unless a separate signed speed observation supports direction.
- Community/scouting may create ordinal edges only when the source itself names or unambiguously defines both sides of a comparison, or when it gives a direction relative to a defined population/band that can be represented without inventing another player.
- Transition evidence must remain temporal/context evidence, not pairwise faster/slower evidence unless a speed measurement before/after supports a signed within-player change.
- Add negative canaries that arbitrary `next()` player selection is impossible in ordinal graph construction.

## Finding 4 — MB-16 multi-lane consensus test is logically inverted

Severity: **P0**

File: `scripts/sp101_repair_and_regenerate_20260818.py`, current-100 route construction.

The code tests:

`len(set([bool(physical available), bool(show available), bool(powerpro available), bool(valid analogs)])) > 1`

This checks whether availability booleans are **mixed**, not whether multiple independent lanes exist.

Consequences:

- if all four lanes are available, the set is `{True}` and the code can classify the player as `INSUFFICIENT_INDEPENDENT_LANES`;
- if exactly one lane is available and the other three are missing, the set is `{True, False}` and the code can classify it as `SUPPORTED_NO_CHANGE`.

Additionally, material conflict detection only compares physical percentile against The Show and PowerPro percentiles. Analog/context/ordinal/transition constraints are mentioned in rationale but do not actually participate in directional conflict logic.

### Required repair

- Count available **independent lane families**, not unique boolean values.
- Require a predeclared minimum number of independent lanes before consensus is possible.
- Define lane-specific comparable outputs/bands and explicit conflict rules.
- Analog similarity, context and transition evidence must affect MB-16 only in ways justified by their semantics; they are not automatically numeric speed bands.
- Add canaries for 4/4 available, 1/4 available, 2/4 agreeing, and 2/4 conflicting cases.

## Finding 5 — MB-18 / route ablation is not actual removal-and-recompute ablation

Severity: **P0**

Files:

- `scripts/sp101_repair_and_regenerate_20260818.py`, `route_receipt()` and route construction;
- `outputs/derived/sp101_route_ablation_qa.json`.

The current receipt convention sets fields such as:

- `pre_ablation_state = EVIDENCE_REMOVED`;
- `post_ablation_state = EVIDENCE_INCLUDED`.

This is the reverse of the normal full-model→route-removed ablation interpretation.

More importantly, route influence is not derived by recomputing the player packet with a route removed. `influence_classification` is hard-coded from evidence presence (for example `CHANGED_EVIDENCE_PACKET`, `CHANGED_BEHAVIOR_MODEL_INPUT`, `CHANGED_TRANSITION_CONTEXT`).

Thus a route with any evidence can be reported as `CHANGED_*` even if removing it would not change:

- route-disagreement state;
- uncertainty band;
- target-selection state;
- owner-review recommendation class;
- any comparable player-level output.

The 1,800 cells prove that receipts exist, not that 1,800 genuine ablations were performed.

### Required repair

- Define a deterministic player-level synthesis state used only for SP-101 evidence integration (not a final SP-079 rating).
- Compute the full state with all eligible routes.
- For each player×route cell, remove that route's evidence and recompute the same synthesis state.
- Store full-state vs ablated-state outputs in correctly named fields.
- Derive influence classification from actual differences, not evidence presence.
- `USED_*` does not imply `CHANGED_*`; a route may be consumed and still be `SUPPORTED_NO_CHANGE` under ablation.
- Add QA proving at least one present-evidence route can have zero decision effect, and that synthetic fixtures with known effects change the expected output.
