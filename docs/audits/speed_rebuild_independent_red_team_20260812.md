## 0. 結論（先に3行）

1. **GPT/Codexのデータ収集は再利用すべき資産**。やり直しが要るのは収集ではなく**最終査定ロジックの設計**。
2. **最大の欠陥は循環**。`practical_powerpro_style_speed` はPowerProをpriorに入れ、PowerProで検証する。一致率は設計上ほぼ自動的に上がるため、**成功指標として機能しない**。

## 3. 現在の再構築案への Red-Team 指摘

### R-1【最重要・循環】priorとQAが同一情報源

`practical_powerpro_style_speed`（§5-B）は入力に PowerPro prior/history・Prospi・The Show変換を含む。
一方 Gate の主要QAは PowerPro 一致率。**priorに入れたものでは検証できない。**

さらに Tier D に PowerPro/Prospi/The Show を全部入れると、**独立QA系統が owner と SNS だけ**になる。
その SNS も Rating Consensus 側は「PowerProの査定が妥当か」という**PowerProについての意見**なので、
独立性がさらに落ちる（→R-7）。
Prospi は PowerPro と情報源を共有している可能性を GPT 自身が §2.10 で懸念しており、
**独立QAとして数えられない**。

gap audit は「PowerPro一致率だけを成功指標にしない」と書くが、**代替の独立軸が実質残っていない**。

### R-2【最重要・オーナー確定ルールの上書き】

ブランチ版 `CLAUDE.md` L52 が次のように書き換えられている:

> 査定の照準は自作エンジン整合 … KONAMI比較は参考チェックに格下げしていたが、
> **走力では2026-08-11追補によりPowerProを強いpriorとして使う**。

これは2026-07-31にオーナーが確定した方針を、**走力だけ例外化する**もの。

**これは2026-08-06に修理した障害と同型である。**
あのとき発見したのは、(a)パワプロ143人への分布合わせ と (b)パワプロの能力値を目標に当てはめた
実測変換式 の2経路が、オーナー確定のアンカー（20本→70 / 30本→80 / 46本→90）を上書きし、
**オーナー自身が「89.8で妥当」と裁定した山川穂高の値が78.9まで落ちていた**という事象だった。

当時の教訓をそのまま適用する:

> ある能力に正本の目安（アンカー）が既にあるなら、その後ろで別の目盛り合わせ・
> 外部ラベルとの混合を重ねてはいけない。

**走力にはアンカーが無いため、この検出器が働かない。**
「上書きされる正本が無い」ので、パワプロ同化が起きても誰も気づけない。これがR-3。

### R-3【構造的欠落】走力にアンカー（目安表）が存在しない

| 能力 | 目盛りの正本 | オーナー裁定 |
|---|---|---|
| パワー | `power_anchors`（20本→70 / 30本→80 / 46本→90） | あり（2026-07-31） |
| ミート | `meet_anchors`（.230→40 / .260→50 …） | あり |
| **走力** | **無し**。`zscore_ratings.speed` は center=50/spread=15 の**自己申告の暫定値**（"パワプロの能力値分布に合わせた暫定値"と自ら記載）＋ `scale_calibration.走力` でパワプロ分布へ寄せている | **無し** |

**走力が常にパワプロへ引き寄せられる真因はここ**。PowerProをpriorに昇格させるのは、
この空白を埋める代わりに**空白を恒久化する**選択になる。

正しい順序は逆で、**物理単位のアンカーを先に作る**:

```text
例（数値はオーナー裁定が必要な仮置き）
  T90 3.85秒 → 走力 90
  T90 4.00秒 → 走力 80
  T90 4.15秒 → 走力 70
  T90 4.30秒 → 走力 60
```

これが出来れば、PowerProは本来の「参考チェック」へ戻せ、R-1とR-2が同時に解ける。
**本red-teamの最重要提言。**

### R-4【実測済みの落とし穴】NPB+ top speed を主軸にする危険は既に定量化されている

```text
top_speed_kmh   train_r 0.640 / train_mae  8.49 / test_r 0.762 / test_mae 10.55 / test_n 14
hp_to_1b_sec    train_r -0.704 / train_mae 7.72 / test_r 0.588 / test_mae 12.90 / test_n 14
```

- **test_r が高く見えても test_n=14**。信頼区間は極めて広い。
- **MAEは10点超**。走力の実用精度として成立していない。

Claude会話期の記録（T-0107）では、走力を瞬間最高速度で置き換えると検出器上 **6.56→7.72 に悪化**。
理由は観測レンジが **29.0〜35.0 km/h と狭く**、傾き 7.32点/km/h が測定誤差を**約7倍に増幅**するため。
実例として矢野雅哉は60打席の実測で **-24.9点** 動いた。半々で混ぜると 6.42 と微改善。
→ だから `blendDirect` は**上書きでなく信頼度加重の混合**として実装されている。

**GPTのblind freezeが「NPB+最高速度中心へ戻ってしまった」のは偶発ではなく、この増幅特性の必然。**
同じ軸で再構築すれば同じ場所に戻る。

### R-5【カバレッジの非対称＝合否基準の破壊】

100人だけを新方式で査定すると、残りの選手と過去年は旧統計モデルのまま。
プロジェクトの正式な合否基準は:

> 12球団×143試合を回した時のリーグ全体の成績分布が実データの分布と一致するか

**同一リーグ内に2つの目盛りが混在すると、この基準自体が評価不能になる。**
盗塁・三塁打・内野安打の分布は走力の絶対水準に直結するため、100人だけ+5点ずれれば
リーグ全体の走塁系指標が歪む。

gap audit の DoD に「engine/simulation QA」はあるが、
**100人と非100人の目盛り整合**は項目に無い。**94項目監査の漏れ。**

### R-6【二重計上】advance と Tier F の衝突

既存実装は 1球データ由来の `advance`（進塁できたか）を**走力の材料**に使い、
**その残差**を走塁得能にしている。

Tier F に "extra-base advancement" を再投入すると、
**同じ1球データ由来の進塁情報を走力へ二重に入れる**ことになる。

プロジェクト第一原則「同じ情報を能力と特殊能力に二重計上しない」に抵触。
`advance` は UBRとの相関0.613（＝4割は別情報）という測定に基づいて足されており、
再投入する場合は**既存の advance と同一物でないことを先に示す**必要がある。

### R-7【SNS二層化】方向は正しいが、Rating Consensus の置き場所が誤り

Physical Observation Consensus と Rating Consensus を分ける案は**妥当**。

ただし Rating Consensus は「PowerProの査定が妥当か」という**PowerProについての意見**であって、
選手の速さについての観測ではない。これを §5-B の入力（evidence list）へ入れると R-1 の循環を強める。

**正しい置き場所は入力ではなく stale detector の材料**。
gap audit §3.3 が「communityでstale/highと複数指摘」を prior弱化条件に挙げているのは正しい使い方で、
§5-B の入力リストに同じものが入っているのが不整合。

### R-8【owner review の母数】PowerPro乖離を基準にすると、人間の労力が同化方向にしか使われない

「|PowerPro diff|>=5 全員をowner review」は、**PowerProからの距離で人間の注意を配分する**設計。
乖離が大きいものだけ見れば、レビューの結果は平均的にPowerProへ寄る。

→ 母数は **証拠の弱さ**（confidence LOW / evidence conflict / exposure不足）へ置き換えるべき。
現状 confidence は MEDIUM 6 / LOW_MEDIUM 87 / LOW 7 で、**87人がLOW_MEDIUM**。
「PowerProと乖離しているか」より「そもそも根拠が薄いか」の方が母数として意味がある。

加えて `12_APPRAISAL_PRINCIPLES` §10 は
「owner feelを教師値にして係数をfitするのは禁止」とする一方、§5-B は owner verdict を入力に入れている。
**個別値としてverdictを尊重するのは可、係数較正に使うのは不可**、という境界の明文化が要る。

### R-9【The Show→PowerPro bridge】原則と手法候補が衝突している

手法比較（direct regression / Statcast intermediary / quantile mapping / isotonic）自体は妥当。

だが `12_APPRAISAL_PRINCIPLES` §9.2 は
「The Show属性がStatcast等を基にしている場合、実測と独立した第二証拠として二重カウントしない」
と定めている。**Statcast intermediary は定義上この禁止に触れる**
（Statcast→The Show→PowerPro と Statcast→直接、の二重使用）。先に裁定が要る。

foreign-player holdout は良い設計。ただし **holdoutの検出力を事前に見積もること**。
NPB+モデルが test_n=14 で誤った自信を与えたのと同型の失敗が起きやすい。

### R-10【validation】入力に使ったものは検証に使えない

「PowerPro一致率だけを成功指標にしない」は正しい。だが代替に挙がる
independent physical fit / owner plausibility / community appraisal は、
**いずれも上流で入力として使う予定のもの**。

本当に独立な検証軸は2つしかない:

1. **時間的ホールドアウト** — 2021-2024の材料で査定を作り、**2025の実プレー結果**
   （三塁打・内野安打・進塁成功・GIDP回避）を予測できるか。
   走力は「速い人は速い結果を出す」という検証可能な帰結を持つ唯一の能力なので、これが使える。
2. **エンジン整合** — リーグ全体を回して盗塁数・三塁打数・内野安打数の分布が実データと一致するか。
   **プロジェクトの正式な合否基準そのもの**。

PowerPro一致率は**参考表示**へ落とす。

### R-11【軸の定義が未確認】

`12_APPRAISAL_PRINCIPLES` §4 は
「NPB+ Sprint SpeedとMLB Statcast Sprint Speedは名称が同じでも数値定義の同一性が確認できていない」
「NPB+ Sprint Speedを確定T90とみなす」ことを**禁止**している。

にもかかわらず100人 blind freeze は NPB+ を事実上の軸にしている。
**軸に据えている量の定義が未確認**という状態。

→ NPB+を軸にするなら、NPB+と direct T90 が両方ある選手で bridge を先に較正する。
現状 current physical measurement は実質モンテロ1件なので、**較正できない＝軸にできない**
という結論になる可能性が高い。その場合、軸は統計材料側に置くしかない。
