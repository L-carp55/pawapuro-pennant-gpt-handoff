# 走力の絶対目盛り（0〜100）— 現時点で自律的に調べられる範囲の結論

作成日: 2026-08-13
状態: **調査完了。正本の目盛りは未確定のまま（別問題として保持）**
根拠: 正本22 §7

---

## 0. 結論（先に3行）

1. **正本22 §7が第一に挙げる「自作エンジンでの応答」は、現時点で実行できない。**
   走力(0〜100) → エンジン入力 の変換が**コードベースに存在しない**（T-0076の未実装部分）。
2. **ただし絶対目盛りは、現在のowner review queueの主因ではない。**
   目盛りをPowerProへ完全に揃えても、|差|>=5 の人数は **51人 → 56人** と**減らない**。
3. したがって §6-7（queue再抽出）へ進んでよい。**目盛りの正本化は独立した宿題として残す。**

---

## 1. §7が挙げる3つの経路の可否

| 経路 | 可否 | 理由 |
|---|---|---|
| 自作エンジン内での走力値→実プレー現象の応答 | **不可** | 走力→エンジン入力の変換が存在しない（下記§2） |
| リーグ全体の三塁打・内野安打・進塁・盗塁の分布 | **部分的に可** | エンジンを通さない分布照合はできるが、目盛りの2自由度（中心・幅）を決めるには不足（下記§3） |
| 既存能力との整合 | **可・実施した** | ミート/パワーはオーナー裁定アンカーを持つ。走力だけ持たない（下記§4） |

## 2. エンジン経路が使えない理由（実地確認）

エンジンは打球結果に `gbSingle`（ゴロが単打になる率の倍率＝走力由来）という調整を受け取る:

```text
src/engine/batted_ball.mjs
  mods = { hrPerFly, gbSingle, xbhBoost }
  p1 = pick('b1', i) * (isGb ? m.gbSingle : 1)
  p3 = pick('b3', i) * (isGb ? m.gbSingle : 1)   // 三塁打の多くはゴロ由来（脚力）
```

**しかし「走力80の選手の gbSingle はいくつか」を決める変換が、コードベースのどこにも無い。**
`gbSingle` を渡している箇所はテストだけで、いずれも literal（1.2 / 0.85 / 1.15 / 1.3）:

```text
scripts/run_bb_engine_test.mjs:95   run({ gbSingle: 1.2 }, SEED)
scripts/test_interactions.mjs:38-49 { gbSingle: 0.85 } / { gbSingle: 1.15 } / { gbSingle: 1.3 }
```

つまり**能力値→エンジンの橋が未実装**（T-0076 Phase2エンジン中核に含まれる）。
この橋ができるまで、「走力の目盛りをエンジン応答で校正する」は**原理的に実行できない**。

→ 目盛りの正本化は **T-0076 に依存する**。これは新しい発見であり、依存関係として記録する。

## 3. 分布照合だけでは目盛りが決まらない理由

エンジンを通さずに「リーグの三塁打・内野安打の分布」と突き合わせることはできる。
だがそれで決まるのは**順位と相対的な間隔**であって、
**0〜100のどこに置くか（中心）とどれだけ広げるか（幅）は決まらない**。

現に、合成zの幅 0.767 は実データから出た値だが、
これを「×15して×1.3811」するのか「×20する」のかを決める根拠は分布側に無い。
**目盛りの2自由度は、外部の基準（アンカー・エンジン応答・オーナー裁定）でしか埋まらない。**

## 4. 既存能力との整合 — 走力だけがアンカーを持たない

| 能力 | 目盛りの正本 | オーナー裁定 |
|---|---|---|
| パワー | `power_anchors`（20本→70 / 30本→80 / 46本→90） | あり |
| ミート | `meet_anchors`（.230→40 / .260→50 …） | あり |
| **走力** | **無し**。`zscore_ratings.speed` は自己申告の暫定値＋`scale_calibration.走力`（PowerPro由来） | **無し** |

正本22 §9 は「ownerに走力の目盛り表を作らせて**停止しない**」と定める。
これは**停止の禁止**であって、アンカーの否定ではない。
現に他の2能力はアンカーで運用されており、走力だけが例外になっている。

→ **目盛りの正本化には、いずれ (a)エンジン応答（T-0076待ち） または (b)オーナー裁定アンカー
のどちらかが要る。** 現時点ではどちらも取れないので、PowerPro由来の較正を
**「暫定・正本ではない」と明示したまま使い続ける**のが唯一の選択肢。

## 5. ★ただし、目盛りは現在のqueueの主因ではない（実測）

候補モデル（統計primary）での実測:

```text
候補モデル   平均 65.8   幅 13.3
PowerPro     平均 65.5   幅 15.5
```

中心はほぼ一致、幅の比は 1.16。ここで**目盛りをPowerProへ完全に揃えたら
差がどれだけ減るか**を測った:

| 判定線 | そのまま | 中心と幅を完全に揃えた後 |
|---|---|---|
| \|差\|>=5 | 51人 | **56人** |
| \|差\|>=8 | 28人 | 35人 |
| \|差\|>=10 | 21人 | 26人 |
| \|差\|>=15 | 8人 | 8人 |

**減らない。むしろ増える。**

つまり残り51人の乖離は**目盛りのずれでは説明できない選手個別の食い違い**であり、
「スケール問題を選手個別の問題としてオーナーに直させる」状態には**なっていない**。

（現行モデルでは違った——較正が98人中1人にしか届いておらず、幅が9.3しかなかったため
差の大半が目盛り由来だった。候補モデルへの切替でその成分が消えた。）

→ **§6-7 のqueue再抽出へ進んでよい。**

## 6. 残す宿題（独立して追う）

- `scale_calibration.走力 slope=1.3811 / intercept=-4.3301` は **PowerPro 143人（2024年）由来**。
  正本ではない。使い続けるが、**教師値とQAの両方にPowerProを使わない**ため、
  100人表のQAではこの点を明示する
- 目盛りの正本化は **T-0076（エンジン中核）依存**。橋ができ次第
  「走力→gbSingle→リーグ分布」で校正する
- それまでの間、走力の絶対値は**順位ほど信用できない**。
  owner reviewでも「何点が正しいか」ではなく「どちらが自然か」を聞く形を維持する
